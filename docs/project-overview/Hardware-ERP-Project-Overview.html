1. What this project is

Hardware ERP is a business system for hardware shops in India. One shop is one tenant. Each tenant's staff sign in, keep their product catalogue and stock, buy from suppliers, sell to customers through quotations, sales orders, delivery challans and GST invoices, record payments and expenses, run customer projects with hired labour, and pull reports including GSTR-1.

It is one Spring Boot application, one React application and one PostgreSQL database. Many shops share that one database; every tenant-owned table carries a tenant_id column and every query filters by it, using the tenant taken from the signed-in user's JWT — never from anything the browser sends. This is the single most important design decision in the codebase (CR-016), and the request-flow diagram in section 3 shows exactly where it is enforced.

Not microservices. Not a database or schema per tenant. Module folders express boundaries, not deployment units. The project is in maintenance and extension, not greenfield: the original twelve-module build order (Auth → Supplier → Customer → Category → Brand → Product → Product Variant → Purchase → Inventory → Quotation → Invoice → Payment) was completed, and later change requests added sales orders, delivery challans, credit notes, projects, labour, expenses, coupons, notifications, reports and the platform console.

Who uses it

Shop ownerCreates staff accounts and roles, sets up branding, bank accounts and WhatsApp, watches the dashboard, runs reports.
Counter staff / salespersonQuotations, invoices, customers, stock lookup — the fast path on a phone or a counter PC.
Purchase staff / inventory managerSuppliers, purchases, bill import, stock adjustments, low-stock follow-up.
AccountantPayments, purchase payments, expenses, receivables ageing, GST summary, GSTR-1.
Project managerCustomer jobs: materials issued from stock, labour attendance, expenses, profitability.
Platform operatorA separate cross-tenant console for incidents, feature flags, subscriptions and support tickets.

3. Application flow — login, JWT and tenant isolation

Read top to bottom. Red paths are refusals; the dashed line is the security audit trail. Files named in the boxes: AuthController, AuthService, TotpService, JwtService, RefreshTokenCookieService, SecurityAuditService (backend); services/apiClient.ts, services/tokenStorage.ts (frontend). 4. Application flow — core business documents

Orange: procure-to-pay. Blue: order-to-cash. Green: catalogue, stock and projects. Purple dashed: discounts. Red dashed: reversal. Every arrow is a real module dependency from MODULE_DEPENDENCY_MAP.md. Stock only ever changes through StockService.applyMovement, which appends a stock_movement row naming the source document; that is why Purchase, Delivery Challan, Invoice, Credit Note and Project Material all point at Inventory.

Document lifecycle rules worth knowing: Quotation, Sales Order and Delivery Challan are optional steps — a counter sale is Customer → Invoice → Payment directly. An invoice is UNPAID → PARTIALLY_PAID → PAID, or CANCELLED; cancelling returns stock. Nothing financial is hard-deleted: users and suppliers are soft-deleted, documents are cancelled, and every change writes an activity_log row with before/after values. Document numbers come from document_sequence under a row lock, so two concurrent invoices cannot collide (CR-041). A retried POST with the same Idempotency-Key replays the stored response instead of creating a second document (CR-051).

6. Roles and permissions

Authorisation is permission-based, never role-based (hard rule 6). A role is only a named set of permissions; business rules check a permission such as INVOICE_CANCEL, never "is the caller an owner". That is what lets an owner create a custom role — say "Senior counter" with INVOICE_DISCOUNT_OVERRIDE — without any code change.

Seeded roleTypical scope
OWNEREverything in the shop, including users, roles, settings, subscription and data reset.
MANAGERDay-to-day operations: products, stock, purchases, sales documents, projects, reports.
ACCOUNTANTInvoices, payments, expenses, purchase payments, reports; no user or settings management.
STAFFCounter work: quotations, invoices, customers, stock lookup.

The 48 permission codes live in the permission table (authoritative) and in auth/entity/PermissionCode.java (so @PreAuthorize strings are compiler-checked; PermissionCodeConsistencyTest asserts the two agree). Families: USER, ROLE, AUDIT, CUSTOMER, SUPPLIER (incl. SUPPLIER_VIEW_BANK_ACCOUNT), PRODUCT (incl. PRODUCT_VIEW_COST, PRODUCT_VIEW_STOCK), INVENTORY, PURCHASE, QUOTATION, INVOICE (VIEW / CREATE / CANCEL / DISCOUNT_OVERRIDE), PAYMENT, EXPENSE, PROJECT, LABOUR, COUPON, REPORT, SETTINGS, DATA_RESET and DEVELOPER_INSPECT (held by no default role).

How a permission is enforced, end to end

  • Backend, the real gate: @PreAuthorize("hasAuthority('INVOICE_CREATE')") on the controller method; the authorities come from the JWT, which was built from role_permission at login.
  • Frontend, for a sensible UI only: RequirePermission hides routes and PermissionGate hides buttons the caller cannot use. Removing them would change nothing about what the API allows.
  • Refusals are recorded: RestAccessDeniedHandler writes an ACCESS_DENIED row to security_audit_log.
  • Platform admins are a different identity with their own table, tokens, MFA and audit log; a tenant-facing controller never calls into platformadmin.

Anatomy of one module: invoice

Every business module has the same seven folders, in the same order the code is written (CLAUDE.md, "specification change" steps 3–4). Reading invoice teaches you all of them.

invoice/…Role
entity/Invoice.java, InvoiceItem.java, Payment.java, InvoiceStatus.java, PaymentMethod.javaJPA entities, one per table; status is a Java enum stored as VARCHAR(20).

What happens inside InvoiceServiceImpl.create(), in one transaction: resolve the customer and check the credit limit → resolve each product and price the line (LineDiscount, rounded to whole paise once) → apply a coupon if given → allocate the invoice number from document_sequence under a row lock → save → StockService.applyMovement(-qty) per line → record coupon usage → write activity_log → after commit, @Async notification. If any step throws, none of it happened.

When a screen shows the wrong thing but Postman shows the right JSON, the bug is in the frontend only — and vice versa. CLAUDE.md requires every bug fix to begin by naming that scope.

Design system rules

  • Never hardcode a colour (hard rule 11): eleven themes × light/dark from theme/colorThemes.ts; components use tokens such as bg-primary, text-muted-foreground, --sidebar.
  • Never draw data that does not exist (hard rule 12): dashboard sparklines and deltas are measured (CR-084), and an empty state says so.
  • A visible redesign is approved as a render first, then coded exactly (hard rule 13) — the sign-in page (CR-081) and dashboard (CR-082) were built that way.
  • Inline "+ Add new X" (category, brand, expense category) uses one shared pattern; BUG-FE-007 documents the Radix Select quirk it must handle.
  • Import flows are always preview → confirm → import, never upload-and-insert (product CSV, supplier bill).

The shape of every change

  1. Name the layer at fault: SCOPE: FRONTEND ONLY / BACKEND ONLY / BOTH.
  2. Claim a CR or BUG number in the registry before writing code (other sessions allocate numbers too — grep first).
  3. For a specification change: registry → new Flyway migration → entity → repository → DTO → mapper → service → controller → tests → types/index.ts → validation schema → service/form/page → Postman → registries.
  4. Fix same-root-cause defects found on the way in the same commit; propose anything bigger as its own CR.
  5. Verify in isolation, quote the numbers, update RESUME_POINT.md, commit with Conventional Commits (feat: fix: docs: …), one concern per commit, body says why.

11. Conventions that never bend

Naming law — one concept, one name, database → entity → DTO → JSON → TypeScript

Only transformationsnake_case → camelCase. credit_limit_paise is creditLimitPaise everywhere.
Tablessingular snake_case; line tables <parent>_item; app_user because user is reserved.
Primary keycolumn <table>_id; Java field always id.
Foreign keycolumn <target>_id; the entity holds the object, the DTO holds <target>Id.
MoneyBIGINT paise, never float or double. BigDecimal only inside LineDiscount / IndianCurrencyFormat, rounded back to paise once.
Unit rates / quantitiesDECIMAL(18,6) / DECIMAL(18,4) — a ₹875 box of 1000 screws is ₹0.875 each.
StatusVARCHAR(20) + CHECK constraint; never TINYINT, never a native ENUM type.
Timestamps / dates / booleansTIMESTAMP(3) suffix _at; DATE suffix _date; booleans without is_.
API paths/api/v1/<plural-kebab-noun>; verbs only under /auth.
Banned aliasesname, phoneNo, phoneNumber, emailId, gstNumber, UserHelper, UserUtil …

Hard rules

  1. Never edit an applied Flyway migration; add a new version.
  2. Hibernate is ddl-auto: validate. Never update.
  3. PostgreSQL only. No MySQL syntax.
  4. Seed data in db/seed/, dev and test profiles only.
  5. No self-registration of users; the owner creates accounts. (New-tenant sign-up is a separate, rate-limited endpoint — CR-028.)
  6. Authorization is permission-based, never hasRole('OWNER').
  7. Users and suppliers are soft-deleted; financial records reference them forever.
  8. Security events → security_audit_log; business changes → activity_log.
  9. Access token in memory only. Never localStorage.
  10. Never claim a build passes without running it.
  11. Never hardcode a colour.
  12. Never draw data that does not exist.
  13. A visible redesign is approved as a render first, then coded exactly.

Git

main (tagged releases) ← develop ← feature/*, bugfix/*; hotfix/* from main back into both. Merge with --no-ff. Runtime environments are Spring profiles, never branches. Several sessions work the same checkout at once, so files are staged by explicit path and CR numbers are claimed in the registry first.
