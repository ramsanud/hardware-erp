# Deployment — free tier

Supabase (database) + Render (backend) + Vercel (frontend), all on free
plans, plus an external keep-alive ping.

Every value you must supply yourself is written as `xxxxxx`. Nothing secret
is committed to this repository.

---

## The one architectural decision that matters

**The frontend and the backend are served from a single origin**, because
Vercel rewrites `/api/*` through to Render.

```
browser ──► https://xxxxxx.vercel.app/            React app (static)
            https://xxxxxx.vercel.app/api/...  ──► https://xxxxxx.onrender.com/api/...
```

This is not a stylistic choice. The refresh token is an **HttpOnly,
`SameSite=Strict`** cookie scoped to `/api/v1/auth`
(`RefreshTokenCookieService`). A `SameSite=Strict` cookie is **never** sent
on a cross-site request, so if the React app called
`https://xxxxxx.onrender.com` directly, the browser would silently drop the
cookie and every user would be signed out the moment their 15-minute access
token expired, with no way to refresh.

The alternatives were:

| Option | Verdict |
|---|---|
| Weaken the cookie to `SameSite=None` | Rejected. It re-opens the CSRF exposure the `Strict` + path scope was chosen to remove, and it is why this API can skip CSRF tokens entirely. |
| Same-origin via Vercel rewrite | **Chosen.** No cookie change, no CORS, and it is exactly what `vite.config.ts` already does in development. |

Because of this, **do not set `VITE_API_BASE_URL` in Vercel.** The app falls
back to a relative `/api`, which is what makes the rewrite work. Setting it
to the Render URL is the single most likely way to break login in
production.

## 1. Supabase — database

1. Create a project. Region: **Singapore** (closest to India).
2. Save the database password somewhere safe. If you have ever pasted it
   into a chat, an email or a commit, reset it now:
   **Settings → Database → Reset database password**.
3. **Settings → Database → Connection string → Session pooler.** Copy the
   host and user from there.

Use the **session pooler on port 5432**, not the transaction pooler on 6543.

> Transaction-mode pooling recycles the connection after every statement,
> which breaks server-side prepared statements and any per-session state.
> `DocumentSequenceService` (CR-041) holds `SELECT … FOR UPDATE` for the
> duration of the caller's transaction to allocate invoice numbers safely;
> under the transaction pooler that guarantee is gone and concurrent
> invoices can collide again. The session pooler is also the IPv4-reachable
> endpoint, which Render needs.

| Render variable | Value |
|---|---|
| `DB_HOST` | `xxxxxx.pooler.supabase.com` |
| `DB_PORT` | `5432` |
| `DB_NAME` | `postgres` |
| `DB_USER` | `postgres.xxxxxx` |
| `DB_PASSWORD` | your reset password |

Flyway runs `V1`–`V29` automatically on first boot. Under the `prod`
profile the `db/seed` files are **not** applied (CR-009), so no demo
accounts or sample shops reach production.

**Free-tier limits:** 500 MB storage, and the project **pauses after 7 days
with no activity**. The keep-alive in step 4 talks to the backend, which
holds a connection pool open, so an actively-pinged deployment does not
pause.

## 2. Render — backend

**New → Blueprint**, point it at this repository. It reads
[`render.yaml`](../render.yaml) and creates the service.

Then fill in every variable marked `sync: false` under
**Environment**:

| Variable | Value | Notes |
|---|---|---|
| `DB_HOST` `DB_USER` `DB_PASSWORD` | from step 1 | |
| `JWT_SECRET` | auto-generated by Render | Or `openssl rand -base64 32`. `JwtSecretGuard` refuses to boot on the built-in placeholder, so a missing value fails the deploy rather than shipping a known key. |
| `CORS_ORIGINS` | `https://xxxxxx.vercel.app` | Only used for direct API access — the browser goes through the rewrite and never makes a cross-site call. |
| `RESET_URL` | `https://xxxxxx.vercel.app/reset-password` | Must be the **frontend** origin. A password-reset email pointing at the API host is a dead link. |
| `APP_BOOTSTRAP_MOBILE` | 10 digits | |
| `APP_BOOTSTRAP_EMAIL` | your email | |
| `APP_BOOTSTRAP_PASSWORD` | a strong password | Change it immediately after first sign-in. |
| `APP_BOOTSTRAP_NAME` | e.g. `Shop Owner` | |
| `MAIL_USER` / `MAIL_PASSWORD` | optional | Gmail **app password**, not the account password. Leave blank and password-reset links are logged instead of emailed — fine for a demo. |

There is no self-registration endpoint by design (CR-008), so
`APP_BOOTSTRAP_*` is how the first OWNER account comes into existence. Once
you have signed in, set `APP_BOOTSTRAP_ENABLED=false` and redeploy.

Copy the service URL — `https://xxxxxx.onrender.com` — you need it twice
below.

**Free-tier limits:**
- Sleeps after **15 minutes** with no inbound request; cold start is 30–60s.
- **750 instance-hours per month for the whole account.** One service kept
  awake around the clock is ~730h, so this budget supports exactly **one**
  always-on free service. A second one exhausts the quota.
- No persistent disk. This app stores uploads as `bytea` in PostgreSQL, so
  nothing is lost on redeploy.

## 3. Vercel — frontend

**Add New → Project**, import the repository.

| Setting | Value |
|---|---|
| Root Directory | `frontend` |
| Framework preset | Vite (auto-detected) |
| Build command | `npm run build` (from `vercel.json`) |
| Output directory | `dist` |
| Environment variables | **none** |

Then edit [`frontend/vercel.json`](../frontend/vercel.json) and replace
`xxxxxx` in the rewrite destination with your Render host:

```jsonc
{
  "source": "/api/:path*",
  "destination": "https://xxxxxx.onrender.com/api/:path*"   // ← change this
}
```

Commit and push; Vercel redeploys automatically.

> **Do not add `VITE_API_BASE_URL`.** See the section at the top.

## 4. Keep-alive and health monitoring

Two independent pingers, because free-tier sleep is what will make the app
look broken in front of a client.

### Primary — UptimeRobot (recommended)

Free plan: 50 monitors at 5-minute intervals, plus a public status page.

1. Sign up at <https://uptimerobot.com>.
2. **Add New Monitor**
   - Type: **HTTP(s)**
   - Friendly name: `Hardware ERP API`
   - URL: `https://xxxxxx.onrender.com/api/actuator/health`
   - Interval: **5 minutes**
3. Add a second monitor for the frontend:
   `https://xxxxxx.vercel.app`
4. Alert contact: your email.
5. Optional: **Status Pages → Add Status Page** gives you a public URL you
   can show a client as evidence of uptime.

`cron-job.org` is an equally good free alternative (down to 1-minute
intervals) if you prefer it.

**Why 5 minutes and not 15:** Render's idle timer is 15 minutes. Pinging
*at* 15 minutes races it. Anything ≤10 minutes has margin for a late or
skipped run.

### Backup — GitHub Actions

[`.github/workflows/keepalive.yml`](../.github/workflows/keepalive.yml)
pings every 10 minutes. To enable it, add a repository **variable** (not a
secret):

**Settings → Secrets and variables → Actions → Variables → New variable**

| Name | Value |
|---|---|
| `API_BASE_URL` | `https://xxxxxx.onrender.com` |

A variable rather than a secret because it is a public URL, and secrets are
masked in logs — which makes a failing ping impossible to read.

Treat this as the backup only. GitHub schedules are best-effort and can run
5–20 minutes late under load, and GitHub silently disables scheduled
workflows on a repository with no commits for 60 days.

### What health actually reports

`GET /api/actuator/health` → `{"status":"UP"}`

Under the `prod` profile that is the **only** actuator endpoint exposed, and
`show-details: never` — so it confirms the app and its database connection
are alive without publishing configuration, beans, mappings or heap
contents. It is the one actuator path `SecurityConfig` leaves public, so the
monitor needs no credential.

## 5. Verify the deployment

In order. Each step fails for a different reason, so do not skip ahead.

```bash
# 1. Backend is awake and can reach the database
curl -i https://xxxxxx.onrender.com/api/actuator/health
#    expect: HTTP 200 {"status":"UP"}
#    504 or a 60s hang -> it was asleep; run it again

# 2. Frontend shell is served
curl -I https://xxxxxx.vercel.app
#    expect: HTTP 200, content-type: text/html

# 3. The rewrite works - THIS is the step that proves same-origin
curl -i https://xxxxxx.vercel.app/api/actuator/health
#    expect: HTTP 200 {"status":"UP"}
#    404 -> vercel.json destination still says xxxxxx

# 4. Login end to end, through the rewrite
curl -i -X POST https://xxxxxx.vercel.app/api/v1/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"identifier":"xxxxxx","password":"xxxxxx"}'
#    expect: HTTP 200, a JSON body with accessToken,
#            and a Set-Cookie header for the refresh token
```

Then in a browser: sign in, leave the tab open past 15 minutes, and confirm
you are still signed in. That is the real test of the cookie decision — if
the rewrite were misconfigured, this is where it would fail.

## 6. Rollback

| Layer | How |
|---|---|
| Vercel | **Deployments → ⋯ → Promote to Production** on the previous build. Instant. |
| Render | **Events → Rollback** to the previous deploy. |
| Database | Flyway migrations are forward-only and additive; there is no down-migration. Restore from a Supabase backup if a migration must be undone. |

## 7. Known limitations on free tier

Say these out loud to a client rather than being caught by them.

| Limitation | Effect | Mitigation |
|---|---|---|
| Render sleeps after 15 min | First request takes 30–60s | Keep-alive (step 4) |
| 750 instance-hours/month | Supports one always-on service | Do not add a second free service |
| 512 MB memory | The JVM must be told the container's limit or it is OOM-killed | `JAVA_TOOL_OPTIONS` in `render.yaml` |
| Supabase 500 MB | Product images are `bytea` and will dominate this | Watch usage; images are the first thing to outgrow it |
| Supabase pauses after 7 days idle | Database unreachable | The keep-alive holds the pool open |
| Vercel rewrite timeout | A cold Render start can exceed it → 504 | Keep-alive; retry the request |
| No custom domain configured | URLs are `*.vercel.app` / `*.onrender.com` | Both platforms allow a custom domain on free |
