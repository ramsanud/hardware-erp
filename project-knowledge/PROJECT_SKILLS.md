# PROJECT SKILLS

Lessons learned. Read before every module; append after every module.

## Naming
1. One concept, one name, across DB → entity → DTO → JSON → React. Only
   `snake_case` → `camelCase` is allowed.
2. A field carrying its own table's prefix drops it inside that table's entity
   and DTO, and re-adds it when embedded elsewhere: `Role.code` but
   `UserResponse.roleCode`. Write the rule down or the next module invents
   `productCode` on the `Product` entity itself.
3. `app_user`, not `user` — `USER` is reserved in MySQL 8.
4. A registry nobody enforces is a document. `registry/check_registry.py` runs
   in CI before `mvn test`.

## Security
5. Never put role or permission data in a JWT. Sign ≠ encrypt, and stale
   authority survives until expiry.
6. `token_version` must be validated against the database on every request, or
   it is decoration.
7. Wrong password, unknown user, locked account and inactive account must return
   byte-identical responses. Any difference is an enumeration oracle.
8. Refresh tokens: opaque random, stored hashed, rotated on use. Reuse of a
   rotated token means theft — revoke every session, do not quietly reissue.
9. Refresh token in an `HttpOnly; SameSite=Strict` cookie; access token in
   memory. Never `localStorage` for either.
10. Sort parameters must be whitelisted and page size clamped. Both are
    injection/exhaustion surfaces.

## Database
11. Flyway owns the schema; Hibernate is `validate`, never `update`.
12. Declare constraints in the database, not only in Java. Java validation is
    for the user; database constraints are for correctness.
13. `status VARCHAR(20)` + CHECK, never TINYINT. `status = 2` is unreadable at
    11pm during an incident, which is exactly when it gets read. On PostgreSQL
    also avoid native ENUM types: adding a value needs `ALTER TYPE`, which does
    not compose well with Flyway.
13a. DDL does not port between engines just because the types line up.
    MySQL's `utf8mb4_0900_ai_ci` made UNIQUE case-insensitive for free;
    PostgreSQL does not, and the guarantee had to be rebuilt as a functional
    index on `lower(col)`. When switching engines, audit the *semantics* of
    every constraint, not just its syntax (BUG-AUTH-009).
13b. Prefer `GENERATED BY DEFAULT AS IDENTITY` over `SERIAL`. It is the SQL
    standard form and the sequence is owned by the column.
14. Seed data belongs in a separate migration range excluded from production.
15. Users are soft-deleted forever — ERP rows reference `created_by` for the
    life of the business.

## Money and quantity (applies from Module 6)
16. Amounts `DECIMAL(15,2)`; **unit rates `DECIMAL(18,6)`**. A ₹875 box of 1000
    screws is ₹0.875 each; at two decimals the box reconciles to ₹880 and the
    loss-sale detector fires on every screw sold.
17. Cost on an invoice line is a **snapshot at sale time**, not a lookup. Master
    price changes must never rewrite history.
18. GST is computed on the final invoice rate, never the master price.

## Process
19. Fix naming defects before locking, not after. Free now, a migration later.
20. Never claim a build passes without running it. State "not executed" and list
    the static checks performed instead.
21. When an instruction contradicts an earlier locked decision, stop and raise a
    change request. Silent reconciliation loses information.
22. Module order follows data dependency, not convenience. Purchase and
    Inventory must precede Invoice, because loss-sale alerts need purchase price
    and stock quantity.


## Module 2 lessons
23. Security audit and business history are two different tables with two
    different readers. Mixing them makes a security review unusable by Module 11
    (CR-015, BUG-SUP-001).
24. Record only the fields that changed, not the whole row. A history table that
    duplicates the table it describes is unreadable and doubles storage.
25. The first two digits of a GSTIN are the state code. If the address state and
    the GST state disagree, one is a typing error - and the consequence is every
    purchase from that supplier being taxed under the wrong head. Validate the
    cross-field relationship, not just each field alone.
26. Put format rules in the database as CHECK constraints as well as in Bean
    Validation. Java validation protects the user; the constraint protects the
    data from every other path - imports, scripts, a second service.
27. "One primary per parent" is a partial unique index
    (`WHERE is_primary = TRUE`), not a service-layer convention.
28. Mask bank account numbers in responses. The last four digits identify the
    account; the full number in every browser cache and screenshot does not.
29. Indian digit grouping is `##,##,##,##0.00` - 5,00,000.00, not 500,000.00.
    Format once in the mapper, using BigDecimal, never with floating point.

## Multi-tenancy retrofit lessons (CR-016)
30. Retrofitting `tenant_id` onto an existing single-tenant table is not just
    a column: every `findById`, every uniqueness check and every "highest
    generated number" query silently assumed one implicit tenant. Grep for
    every repository method against a table before declaring it tenant-safe
    - `findById` specifically, since it compiles fine and returns a row from
    any tenant.
31. Decide login-identifier uniqueness scope (global vs per-tenant) before
    writing the migration, not after. Global uniqueness for `mobile_no`/
    `email` was chosen deliberately here because login has no tenant
    selector - re-deriving that decision per module wastes time and risks
    disagreeing with itself.
32. A field you do not want silently overwritten needs the same masking
    discipline as a bank account number - see lesson 33.

## Module 3 lessons (Category, Brand, Product)
33. Permission-gated response fields (here: `PRODUCT_VIEW_COST` nulling
    purchase price) create the same silent-overwrite risk BUG-SUP-BANK
    already taught for bank account numbers, but on any entity, not just
    Supplier. If an update endpoint requires the field on every request and
    a viewer can't see the current value, gate the *edit action itself* on
    holding both the manage and the view-cost permission - do not let the
    edit form open with a blank/zeroed value that then overwrites the real
    one on save.
34. When new-module business rules conflict with a fresh, more detailed
    instruction (here: CR-004's Product Variant-only pricing vs. a request
    to put pricing directly on Product), write the deviation into
    FEATURE_REGISTRY.md as its own dated section, not just a passing
    comment in code - the next person (or the next session) needs to find
    the reasoning without re-deriving it from a diff.
35. A hierarchical lookup table (Category, self-referencing
    `parent_category_id`) needs its delete guard to check both directions:
    referenced by a child row of the *same* table (a sub-category) and
    referenced by a row of a *different* table (a product). Checking only
    one direction leaves an orphaning bug.

## Module 8 lessons (Project Management)
36. When a new entity is modelled after an existing one *because* that
    entity omits something (BUG-PROJ-001: `ProjectMaterial` copied
    `InvoiceItem`'s "plain fields, no `BaseEntity`" shape, but added back a
    `created_at` column `InvoiceItem` never had), copying the shape without
    copying the *reason* for it is exactly how a bug like this happens. A
    plain (non-`BaseEntity`) timestamp column needs its value set explicitly
    at the point the entity is built - verify with a test that inspects the
    entity actually passed to `save()` (`ArgumentCaptor`), not just that
    `save()` was called.
37. `ddl-auto: validate` catching a migration that forgot columns
    `BaseEntity` requires (`work_type`'s `V18` missing `created_by`/
    `updated_by`) is the system working as designed, not a failure - but it
    only catches it at the *next real startup*, not at compile time. Any
    entity extending `BaseEntity` needs its migration checked against
    `BaseEntity`'s four audit columns explicitly, the same way every other
    entity-vs-migration column check already happens in this codebase.
38. A generic `DataIntegrityViolationException` handler that returns "This
    record conflicts with existing data" is correct behavior for an actual
    unique-constraint violation, but the *same* generic message also covers
    every other constraint class (NOT NULL, FK, CHECK) - when live-testing
    surfaces this message, read the actual backend log line before assuming
    it's a duplicate-key issue. The real SQL error is one log line away and
    was the fastest path to the real root cause here.
39. "Does this number make real-world sense" is a testing technique in its
    own right, independent of whatever feature is being explicitly tested.
    BUG-INV-001 (a product at -1 ROLL on hand) was found not by testing
    Invoice or Stock directly, but by glancing at a Dashboard number during
    an unrelated re-crawl and asking whether a shop can physically have
    negative units of a hammer. When a single method is the one choke point
    every caller passes through by design (here, `StockServiceImpl
    .applyMovement()` - CR-021), a missing invariant there is worth fixing
    at that one point rather than duplicating a check in every caller.
40. When a wizard's customer field is deliberately free text rather than a
    picker (CR-021's original design - see #39's neighbor, unrelated to it),
    a feature that needs to know about an *existing* customer mid-entry
    (credit-limit warning, CR-030 §17) still needs a real lookup - grep for
    an existing exact-match repository method (`findByTenantIdAndMobileNo`
    existed already) before assuming a new one is needed, and prefer a 404
    for "no match" over inventing a found/not-found wrapper shape - the
    frontend already has to handle ApiError everywhere, so treating "not
    found" as a normal, silently-swallowed case (not every 404 is a bug)
    is less code than a bespoke response envelope.
41. Before building a new "one sanctioned gate" service, check whether one
    already exists for a *sibling* concern and copy its shape rather than
    inventing a new one. CR-031's `EntitlementService` (numeric per-tier
    limits) is structurally identical to the `SubscriptionService`
    (feature-tier gating) that already existed from CR-027 - same tenant
    lookup, same "throw a typed BusinessException before anything is
    built" contract, same one-method-per-thing-being-gated shape. Finding
    and mirroring that precedent first meant the new service needed no
    design decisions of its own, only the numbers.
42. To live-verify a limit/quota feature without seeding thousands of fake
    rows, look for a tenant that already has real data past the limit by
    accident - CR-031 tested FREE-tier's 100-customer cap by temporarily
    flipping the primary test tenant (already at 1,000+ customers from
    earlier load-testing, CR-028) to FREE, confirming the rejection, then
    switching it straight back to MAX and re-verifying a real create
    still worked, and confirming via a direct DB query afterward that the
    tenant's tier actually landed back where it started. Faster and more
    realistic than constructing a fresh tenant and creating 100 records
    - but only safe when the restore step is unconditional (a `finally`
    block, not just the next line) and is itself verified, not assumed.
43. A parent component's `loading` flag that gates an early return (`if
    (loading) return <Spinner />`) unmounts every child underneath it just
    as completely as a hard page reload does - just less obviously, since
    nothing in the code says "reload." BUG-FE-006 (CR-032) needed two
    separate fixes for the same symptom (a success message disappearing
    before it could be seen): first an actual `window.location.reload()`,
    then - after removing that - the parent's own `reload()` helper still
    flipped `loading = true` and unmounted the child a second, subtler way.
    When a success message must survive a success-triggered refetch, lift
    the data the parent needs into a callback and patch state directly
    (no loading flip), rather than assuming "I removed the reload call" is
    the same as "this component won't unmount."
44. When a lazily-reverting piece of state (CR-032's trial-expiry check in
    `SubscriptionServiceImpl.currentTier()`) needs to write on read, mark
    that method `Propagation.REQUIRES_NEW`, not just non-`readOnly`. A
    method's own `@Transactional(readOnly = false)` is meaningless once
    it's called from inside a caller's `readOnly = true` transaction -
    `REQUIRED` propagation (the default) joins that same physical
    transaction, and Hibernate's flush-suppression for a readOnly
    transaction applies to the whole thing, not per-method. Caught by
    tracing every call site (`EntitlementServiceImpl`'s checks,
    `TenantSettingsServiceImpl.get()`, both readOnly) before shipping,
    not by a test failure - worth doing for any "write as a side effect
    of a read" design before assuming the write will actually happen.
45. When `npm run <script>` or `npx <tool>` fails in this project's
    git-bash shell with `'"node"' is not recognized as an internal or
    external command` (a broken `.cmd` shim, not a real Node/PATH
    problem - `node --version` and `which node` both succeed fine), the
    workaround is to call the tool's JS entrypoint directly with `node`:
    `node ./node_modules/typescript/bin/tsc -b --force`, `node
    ./node_modules/vite/bin/vite.js build`, etc. This has recurred across
    several rounds (CR-030 §17/§45-46, CR-033) - it's an environment
    quirk of this shell, not a code issue each time, and re-diagnosing it
    from scratch wastes a round; just use the direct-binary form.
46. Live UI verification (Playwright or similar) should never reuse a
    real user's real credentials, even when they were shared earlier in
    the conversation for a different purpose (e.g. Gmail SMTP setup) -
    writing them into a throwaway test script is an unnecessary handling
    of a real secret, and driving the actual owner account risks
    polluting real data. This app's own `POST /v1/tenants/register`
    (public, CR-028) is the cleaner path: register a disposable
    synthetic tenant (fake shop name, fake mobile/email) for exactly the
    scope of the verification, and say plainly in the writeup that a
    leftover throwaway tenant now exists in the dev database rather than
    silently leaving it unexplained.
47. Playwright's `page.locator('button', { hasText: 'X' })` substring-
    matches the element's *entire* text content, including any prose
    sitting near the real target - not just a short visible label. CR-034's
    verification script clicked the wrong element three separate times
    because "Flat" is a substring of "inflated" and "stay flat" in nearby
    design-style description text, and `.first()` silently picked one of
    those instead of erroring. The button never being clicked meant a real
    bug (the Elevation control) went briefly undiagnosed as "the app is
    broken" when it was actually "the test picked the wrong element."
    Fix: scope segmented-control/exclusive-choice assertions to a stable
    container first (`[role="group"][aria-label="..."]`), then locate the
    button inside it - don't rely on a short label being unique across the
    whole page, especially one sitting next to freeform description text.
48. A CSS custom property "protect this specific value from a
    transformation" rule should never be keyed off the value's own
    *magnitude* (e.g. "skip alpha values <= 0.08") when nearby, unrelated
    values can coincidentally fall in the same range. CR-034's
    `scaleShadowAlpha()` tried to spare Liquid Glass's faint highlight
    line from the Elevation dial's scaling by exempting any alpha <= 0.08
    - but Minimal's own base shadow alpha (0.05) is even fainter, so it
    got exempted too, silently breaking Elevation=Flat for the app's
    default style. Fixed by detecting the thing to protect *structurally*
    (its literal `inset 0 1px 0 0 rgb(255 255 255...)` shape) instead of
    by how faint it happened to be. General lesson: prefer structural/
    identity checks over magnitude thresholds when two different concepts
    can plausibly share a numeric range.
49. `net::ERR_INSUFFICIENT_RESOURCES` appearing after many consecutive
    client-side SPA navigations in one long-lived browser tab is a real,
    reproducible Vite **dev-server** artifact on this project, not
    necessarily an application bug - found while demo-hardening ahead of
    a same-day customer demo. A single page load in `vite dev` mode fires
    roughly 180 separate unbundled ES-module HTTP requests (confirmed via
    request-log breakdown on Shop Settings), each doubled again by React
    18 StrictMode's dev-only double-effect invocation; accumulated across
    ~15+ rapid route changes in one tab this hits a real Chromium per-tab
    pending-request ceiling. Root-caused by re-running the identical
    crawl against a production build (`vite build` + `vite preview`) and
    confirming zero errors - production collapses to 4 JS + 1 CSS file
    and StrictMode's double-invoke doesn't apply outside dev mode. Before
    chasing a "some pages randomly break after clicking around for a
    while" report as an application bug, rule this out first: does it
    reproduce against a production build? If not, it's dev-server
    request volume, not the app. For a live demo specifically, serve the
    production build (`vite preview`) rather than `vite dev` regardless -
    faster, quieter, and removes this whole class of risk.
50. When a bulk-import confirm loop creates a *new* row-level entity per
    row (CR-035's Supplier Bill Import creating Products), two rows in
    the same batch naming the identical new entity will crash the second
    creation attempt if each row calls the ordinary single-create service
    method independently - the first row's create() has already claimed
    the unique name/code within the same transaction, so the second
    row's create() correctly rejects it as a duplicate. Found live,
    testing a real 100-row bill, not from a hand-written unit test (the
    unit tests never happened to construct two rows with the same new-
    entity name). Fix: track already-created entities by their natural
    key within the batch's own scope (a local `Map<normalizedName,
    Entity>`) and reuse the earlier one instead of re-creating - this is
    a different failure mode than "matching an existing DB row," and the
    result summary needs a *third* counter for it (not lumped into
    "existing matched," which would overstate how much of the catalogue
    pre-existed) - see lesson 51.
51. A bulk-operation result summary must not silently conflate two
    different "already handled" reasons into one counter just because
    they end up not creating a new row. CR-035's Supplier Bill Import
    result screen originally reported "existing products matched" for
    both genuine pre-existing catalogue matches *and* rows that reused a
    product this same import batch had just created a few rows earlier -
    both are real and both are correct behavior, but merging them into
    one number overstates how much of the catalogue already existed
    before this import ran. Caught only by actually reading the number on
    screen after a live test and noticing it didn't match hand-counted
    expectations, not by any test assertion. General lesson: when adding
    a "reason X happened" counter to a result/summary screen, ask whether
    there's a second distinct reason the same code path can be reached,
    and give it its own counter rather than reusing the first one that
    fits mechanically.
52. `curl -F "field=$(cat file.json)"` fails with "Argument list too
    long" once the file gets into the hundreds-of-KB range on
    Windows/git-bash, because `$(cat ...)` inlines the entire
    file content as a single shell command-line argument, and Windows
    has a real (much lower than Linux) total command-line length limit.
    Found testing CR-035's Supplier Bill Import confirm endpoint with a
    real ~1000-row JSON payload. Fix: use curl's own file-reference form
    field syntax instead - `-F "field=<file.json;type=application/json"`
    (note the `<`, not `@`) - which streams the file's contents directly
    into the multipart body without ever passing it through the shell's
    argument list. Worth remembering any time a multipart test needs a
    JSON part larger than a few KB.
53. This session's ephemeral scratchpad directory can be wiped mid-task
    more than once, not just as a single early-session incident - lost
    an installed `playwright` node_modules a second time during CR-035's
    live testing, well after the first documented wipe. The *parent*
    scratchpad directory (holding real generated test fixtures and a
    separately-installed `xlsx` package) survived both times - only a
    specific subdirectory got cleared. Reinstalling a lost npm package
    takes seconds and isn't worth being alarmed about, but never treat
    the scratchpad as reliably persistent within a single session, and
    prefer keeping durable dev artifacts (like `.env`, per the earlier
    documented incident) outside it entirely.
